## `release.sh` : les tests .NET tournent à part, un fichier exclu

Premier passage arrêté par `windowsDesktopMissionPath.test.ts` (« Construire manuel : la carte reste obligatoire », aucune carte parce que la mission n'avait pas fini dans ses délais sous la charge de la suite complète : 109 s pour le fichier contre 71 s seul, 6/6 verts seuls). Le même fichier avait arrêté la publication 5.0.71 (EBUSY). `release.sh` lance maintenant la suite du bureau sans les deux fichiers qui exécutent dotnet, puis ces deux fichiers seuls quand le SDK est là ; sans SDK, le comportement d'avant (fichiers ignorés). Le test affirme désormais que la mission a fini (avec son résumé) avant de chercher la carte.

Deuxième passage : arrêté par le même test, cette fois avec la raison : « Bloqué : typecheck n'a pas été lancé » (la mission simulée a fini en échec). Rejoué ensuite 8 fois (seul avec `-t`, puis le fichier entier, avec une trace temporaire retirée depuis) : **8 échecs sur 8**, alors que le même test était vert à 15 h 29 (suite complète) et à 15 h 45 (fichier seul). Trace : la mission « Appli Windows .exe minimaliste » choisit le gabarit par règles rapides (`fastDesign`, nom « Appli Windows exe » tiré de la demande), le plan du faux modèle vise `src/ManuelBuild.Core/Salutation.cs` qui n'existe pas dans ce projet, le plan de secours demande les fichiers d'entrée du gabarit, le faux modèle ne sait pas les écrire → « aucune modification » → mission en échec, aucune série de tests. Pourquoi ce même test passait avant n'est pas établi. Il ne touche pas au code publié dans cette version (aucun changement dans Jarvis Développeur).

**Décision de l'utilisateur** (question posée, réponse « Publier en excluant ce test ») : `release.sh` exclut `windowsDesktopMissionPath.test.ts` depuis la 5.0.72 ; `dotnetProject.test.ts` tourne toujours seul quand le SDK est là ; tout autre test rouge arrête la publication. À réparer dans une prochaine version, puis à remettre dans le script.
